TARGET APP FILE TREE V5 — RESTAURANTPOS-LARAVEL
Final stricter 10/10 target architecture for app/

GOAL
- Final target structure for long-term development of RestaurantPOS-Laravel.
- Optimize simultaneously for:
  - domain modularity
  - layer clarity
  - consistency
  - separation of concerns
  - operational maturity
  - maintainability
  - onboarding clarity
  - scalability of code organization
  - professional naming / ownership
  - anti-drift enforceability

QUALITY IMPROVEMENTS IN V5
- No empty placeholder folders are shown in the tree. Optional subfolders are only created on first real use.
- No pseudo-lane folders such as Shared/Common are used inside module Http. Cross-lane HTTP artifacts live directly under Http/Resources or Http/Concerns.
- Platform no longer uses generic Application/Services. It uses sharper capability folders such as Builders / Inspectors / Verifiers / Resolvers / Gates / Packagers / Reporters / Propagators / Coordinators.
- Opaque operational names are removed. Prefer explicit names such as RuntimeHealthInspector or ReleasePromotionGate over vague / project-internal names.
- Generic “manage everything” handlers/controllers are removed where a more precise intent can be named.
- Generic catch-all read-model classes are removed. Reporting and local read-side artifacts must be concrete and ownership-specific.
- Infrastructure naming is standardized around Persistence / ReadModels / Projections / Caching / Integrations / Queue / Streaming / Files / Internal.
- Cross-module publishing is made explicit through IntegrationEvents where module boundaries matter.
- SharedKernel remains only for stable business primitives. Technical helpers remain in Support. Platform remains operational only.
- MasterDataExchange remains exchange-only and registry-driven; it never becomes an admin super-module or a hidden business runtime owner.

ARCHITECTURE POSITIONING
- Modular Monolith by domain ownership.
- Clean-ish / DDD-lite at module level, still pragmatic for Laravel.
- Business runtime lives only in app/Modules/*.
- Framework edge concerns stay in top-level app/Http.
- Cross-domain business primitives stay in app/SharedKernel.
- Technical support stays in app/Support.
- Operational / governance / delivery capability stays in app/Platform.
- No return to top-level legacy business lanes.

FINAL ARCHITECTURE VERDICT
- This is NOT Layered Monolith.
- This is NOT actor-driven foldering.
- This is NOT “half module, half random service dump”.
- This is a disciplined Modular Monolith with explicit platform isolation and explicit anti-drift rules.

NON-NEGOTIABLE LAWS
1. app/Modules/* is the only home of business runtime.
2. app/Http only contains framework-level HTTP concerns:
   - base controller
   - global middleware
   - exception rendering / translation
   - edge-only HTTP helpers
3. app/Support only contains technical/framework support with no business ownership.
4. app/SharedKernel only contains stable cross-domain business primitives.
5. app/Platform only contains operational, governance, delivery, quality, and runtime-control concerns.
6. Actor lanes are allowed ONLY inside module Http:
   - Guest
   - Customer
   - Staff
   - Admin
   - Webhook
   - Internal
7. Module names must be domain/capability names, never actor names.
8. No top-level business folders such as:
   - app/Models/*
   - app/Services/*
   - app/Http/Controllers/Api/*
   - app/Http/Requests/*
   - app/Http/Resources/*
9. Cross-module interaction is allowed only via:
   - Application/Queries
   - Application/Commands or Application/UseCases
   - Domain/Events or Domain/IntegrationEvents with explicit owner workflow/listener
10. No module may directly import another module’s Http or Infrastructure implementation.
11. SharedKernel is not a dumping ground. “Used in many places” is NOT enough to move something there.
12. Support is not a dumping ground. “Convenient helper” is NOT enough to move something there.
13. Platform must never own business flow runtime.
14. Reporting must never become the owner of business mutation logic.
15. MasterDataExchange must never become a generic “admin super-module”.
16. When a module grows, split by sub-area inside the module first; only create a new module when the domain boundary is real and stable.
17. Generic *Service.php naming is forbidden when a more specific name is possible:
   - Handler
   - Workflow
   - Policy
   - Guard
   - Rule
   - Specification
   - Projector
   - Mapper
   - Factory
   - Builder
   - Inspector
   - Verifier
   - Resolver
   - Packager
   - Reporter
   - Propagator
18. Domain/Services is allowed only for pure domain logic:
   - no HTTP
   - no persistence orchestration
   - no external integration
   - no transaction script dumping
19. Actor-named subfolders are forbidden outside module Http.
20. Optional folders are created only on first real file, never as empty ceremony.
21. Inside Http actor lanes, file basenames must stay actor-neutral:
   - AuthController.php, not CustomerAuthController.php
   - ReservationController.php, not StaffReservationController.php
22. Module-private technical helpers belong to Infrastructure/Internal, not Infrastructure/Support.
23. Bank / settlement / payout ownership belongs to finance modules unless the object is strictly credential / identity scoped.
24. Read-side ownership must be explicit:
   - Infrastructure/ReadModels for local query models
   - Infrastructure/Projections for reporting or integration projections
25. Common cross-lane HTTP artifacts live directly under module Http/Resources or module Http/Concerns, never under pseudo-lane folders such as Shared or Common.
26. Platform/Application must not use generic Services folders.
27. Generic umbrella controllers / handlers such as ManageXxx or ReportingController are forbidden when sharper use-case naming is possible.
28. Generic catch-all read model classes such as XxxReadModel.php are forbidden in business modules and reporting modules.
29. Infrastructure foldering should prefer the standard vocabulary:
   - Persistence
   - ReadModels
   - Projections
   - Caching
   - Integrations
   - Queue
   - Streaming
   - Files
   - Internal
30. Import / export modules may coordinate exchange only; they must not quietly become owners of domain runtime rules.

NAMING LAWS
1. Module names: PascalCase, domain/capability noun, no Admin/Customer/Staff prefix.
2. Application folders: DTOs / Commands / Queries / UseCases / Workflows / Contracts. Only create each folder on first real use.
3. Domain folders: Models / Enums / Policies / Rules / Events / IntegrationEvents / ValueObjects / Services / StateMachines / Specifications / Factories. Only create each folder on first real use.
4. Http folders: Controllers / Requests / Resources / Concerns. Lane split must be actor-consistent. Once inside a lane folder, basenames must be actor-neutral.
5. Infrastructure folders: Persistence / ReadModels / Projections / Caching / Integrations / Streaming / Queue / Files / Internal depending on module need.
6. UseCases are intent-specific, not generic “manager” dumping classes.
7. Workflows are orchestration-heavy, multi-step, or cross-policy flows.
8. Request / Resource / Controller naming must follow the same lane strategy across all modules.
9. Sub-area names inside a module must be domain-oriented, not random technical names.
10. Read models belong either:
    - to the producing module for local queries under Infrastructure/ReadModels
    - or to Reporting under Infrastructure/Projections when they are explicitly reporting projections
11. Empty optional folders are not scaffolded until first use.
12. Actor qualifiers in file names are allowed in Application only when they clarify intent, not as foldering strategy.

TOP-LEVEL RULES
- app/Models: forbidden for business models.
- app/Services: forbidden for business services.
- app/Http/Controllers/Api: forbidden.
- app/Http/Requests: forbidden for business requests.
- app/Http/Resources: forbidden for business resources.
- app/Enums: only truly global technical enums.
- app/Casts: only truly global technical casts.
- app/Jobs: if needed for business runtime, place under the owning module or Platform if purely operational.
- app/Events / app/Listeners: if business-owned, place under the owning module; if platform-owned, place under Platform.
- module-private technical helper folders: use Infrastructure/Internal, never Infrastructure/Support.

MODULE BOUNDARY DECISIONS
1. Billing is split from Payments and Cashiering.
   - Billing owns bill composition, invoice generation rules, financial summaries.
   - Payments owns payment sessions, provider interactions, captures, refunds, webhook receipts.
   - Cashiering owns staff checkout, cashier shifts, settlement, reconciliation.
2. Loyalty is split from Promotions.
   - Loyalty owns points, tiers, earn/burn, ledger sync.
   - Promotions owns vouchers, benefits, promotion policy evaluation.
3. InventoryProcurement stays as one module but is split internally into:
   - Inventory
   - Procurement
4. BranchScheduling stays as one module but is split internally into:
   - Branches
   - Tables
   - Availability
   - Holds
5. Conversations remains a dedicated module, not hidden under Reservations or Notifications.
6. Notifications remains channel/runtime delivery oriented, not a miscellaneous communication dump.
7. Reporting remains read/projection/report oriented only.
8. PrivacyCompliance remains compliance/audit/redaction oriented only.
9. Actor segmentation is an HTTP concern only; it must not leak into Application folder topology.
10. Local read models stay with the owning module; reporting-wide projections belong to Reporting.
11. FloorOperations owns in-service floor runtime only; it must not absorb reservation ownership.
12. MasterDataExchange owns import/export coordination and registry resolution only; it must not own branch/menu/loyalty business logic.

OPTIONAL FOLDER PRINCIPLE
- Folders such as DTOs / Commands / Queries / Contracts / Services / StateMachines / Specifications / IntegrationEvents / Projections / Internal are created only when the first real class justifies them.
- The target tree below intentionally avoids empty symmetry folders.
- Symmetry is not a design goal; clarity of ownership is.

ANTI-DRIFT CHECKLIST
1. If owner domain is unclear, the file must not be created yet.
2. If the code changes business state, it must live under an owning module.
3. If the code is only HTTP adapter logic, it belongs in module Http or top-level app/Http if globally shared.
4. If the code is a stable business primitive used by multiple modules, consider SharedKernel.
5. If the code is only technical support with no business meaning, consider Support.
6. If the code is deployment / health / metrics / verification / release / runtime control, consider Platform.
7. Never create new top-level business folders just because the module feels “far away”.
8. Never place cross-module orchestration in Support.
9. Never place business-specific runtime settings in Platform.
10. Never place operational probes inside business modules unless the probe is module-owned and strictly local.
11. Never create actor-named subfolders outside module Http.
12. Never repeat actor qualifiers in Http file basenames when the folder already expresses the lane.
13. Never introduce empty symmetry folders just because other modules have them.
14. If a model smells financial, do not place it in IdentityAccess by convenience.
15. If a module-private helper does not deserve a named technical subfolder, do not create Internal yet.
16. Never reintroduce pseudo-lanes like Shared/Common inside module Http.
17. Never create generic umbrella controllers / handlers when a use-case-specific name is available.
18. Never create generic reporting / read-model base artifacts that hide ownership.

FORBIDDEN / REMOVED FROM TARGET STRUCTURE
- app/Models/*                                  -> forbidden for business models
- app/Services/*                                -> forbidden for business services
- app/Http/Controllers/Api/*                    -> forbidden
- app/Http/Requests/*                           -> forbidden for business requests
- app/Http/Resources/*                          -> forbidden for business resources
- top-level actor folders                       -> forbidden
- generic business helper classes in Support    -> forbidden
- module-private technical helpers in Support   -> forbidden; use Infrastructure/Internal
- cross-module direct Infrastructure imports    -> forbidden
- reporting-owned business mutations            -> forbidden
- master-data-owned business runtime            -> forbidden
- module Http pseudo-lanes Shared/Common        -> forbidden
- Platform/Application/Services                 -> forbidden
- generic manage/report/read-model artifacts    -> forbidden when sharper ownership is possible

PLACEMENT LAW
- New business code                             -> app/Modules/<Domain>/...
- New module HTTP adapter                       -> app/Modules/<Domain>/Http/*
- New framework-edge middleware / renderer      -> app/Http/*
- New pure domain rule / policy / spec          -> app/Modules/<Domain>/Domain/*
- New orchestration / transaction script        -> app/Modules/<Domain>/Application/UseCases or Workflows
- New external adapter / persistence / cache    -> app/Modules/<Domain>/Infrastructure/*
- New stable cross-domain business primitive    -> app/SharedKernel/*
- New technical helper with no business owner   -> app/Support/*
- New operational / governance capability       -> app/Platform/*

FINAL QUALITY BAR
To stay 10/10 over time, every pull request should be rejectable on folder ownership alone if it violates:
- domain ownership
- layer intent
- actor-lane discipline
- module boundary rules
- shared/support/platform laws
- no-empty-ceremony rule
- no-actor-lane-leakage rule
- no-pseudo-lane-inside-Http rule
- no-generic-umbrella-artifact rule
