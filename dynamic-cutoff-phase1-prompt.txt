# Dynamic Cutoff + Partial Refund Optimization for RestaurantPOS

## Intent
Implement revenue-optimal cancellation policy: extend refund deadline based on advance booking days,
and apply graduated refund percentages when customers cancel late. This maximizes table rebooking
opportunity while maintaining customer fairness.

## Priority: Phase 1 (Dynamic Cutoff Only)
Focus on dynamic cutoff calculation first. Partial refund is Phase 2.

---

## Business Rules (Phase 1)

### Current Behavior (Fixed)
```
All bookings: deadline = start_time - 30 minutes
Result: 5-day advance booking loses 4+ days of rebooking window
```

### Optimal Behavior (Dynamic)
```
Hours until start_time → Cancellation cutoff:
  ≥ 72 hours (3+ days) → 2 days before start_time
  ≥ 48 hours (2 days)  → 1 day before start_time
  ≥ 24 hours (1 day)   → 4 hours before start_time
  ≥ 2 hours            → 30 minutes before start_time
  < 2 hours            → 0 minutes (NO cancellation allowed)

Example:
  Booking: Monday 10:00 → Friday 12:30 (72 hours)
  Current deadline: Friday 12:00 (0.5 hours for rebooking)
  NEW deadline: Thursday 12:30 (24 hours for rebooking) ← 48x better!
```

### Refund Behavior (UNCHANGED for Phase 1)
- When cancellation allowed → refund 100%
- When cancellation NOT allowed (quá hạn) → refund 0% (current behavior)

## Remaining Risks (Phase 1)

### Risk: Performance
- **Impact**: New date calculation on every cancellation check
- **Mitigation**: Calculator uses only `now()` and `start_time` (already in memory)
- **Verification**: Load test 1000 concurrent cancellation preview requests
- **Acceptance**: < 50ms per calculation

### Risk: Timezone Bugs
- **Impact**: DST transitions, multi-timezone branches
- **Mitigation**: Always use UTC internally, convert only for display
- **Verification**: Test Australia (DST in Sept), Europe (DST in March)
- **Acceptance**: Deadline consistent across timezones

### Risk: Customer Communication
- **Impact**: Existing customers expect 30-minute cutoff
- **Mitigation**: Feature flag (rollout to 10% first), email notification
- **Verification**: Monitor support tickets about "why can't I cancel anymore?"
- **Acceptance**: < 2% increase in cancellation-related support

### Risk: API Breaking Change
- **Impact**: Staff/Customer frontends may not expect new fields
- **Mitigation**: Add fields, don't remove. Frontend optional consumption.
- **Verification**: Existing field read tests still pass
- **Acceptance**: Zero 4xx errors from unknown fields
